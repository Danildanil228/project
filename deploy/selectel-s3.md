# Пользовательские файлы в Selectel S3

Приложение использует S3 только для растущего пользовательского контента:

- фотографий постов;
- аватаров, загруженных с компьютера.

Каталог рыб, приманок, удилищ и катушек, карты, 3D-модели и пользовательские звуки пока остаются в `back/uploads`. Старые локальные фотографии также продолжают работать после включения S3.

## 1. Создание бакета

1. Откройте панель Selectel.
2. Перейдите в **Продукты -> S3 -> Бакеты**.
3. Создайте бакет, например `rf4-user-content`.
4. Выберите **стандартный** класс хранения: эти изображения будут регулярно открываться на сайте.
5. Выберите **публичный** тип бакета. Публичность нужна только для чтения изображений браузером. Загрузка и удаление по-прежнему требуют S3-ключ.
6. Не включайте Object Lock для этого бакета: приложение должно иметь возможность удалить фотографию вместе с постом.
7. На вкладке конфигурации бакета найдите и сохраните:
   - публичный домен бакета, похожий на `https://<uuid>.selstorage.ru`;
   - имя бакета;
   - пул/регион бакета.

Не добавляйте CDN на первом этапе. Сначала нужно проверить обычный публичный домен S3 и собрать фактическую статистику трафика.

## 2. Сервисный пользователь и права

Не используйте ключ владельца аккаунта.

1. Откройте раздел управления доступом Selectel.
2. Создайте отдельного сервисного пользователя, например `rf4-media-api`.
3. Выдайте ему роль `s3.bucket.user` для проекта с созданным бакетом.
4. Откройте бакет -> **Политика доступа**.
5. Добавьте правило для сервисного пользователя:
   - доступ: разрешить;
   - пользователь: `rf4-media-api`;
   - набор действий: редактор;
   - ресурс: `rf4-user-content/user-content/*` (замените первую часть, если бакет назван иначе).
6. Создайте для сервисного пользователя S3-ключ.
7. Сохраните `Access key` и `Secret key`. Secret key показывается только при создании.

Публичному посетителю сайта не выдаётся этот ключ. Он существует только в `.env` backend-сервера.

## 3. Адрес S3 API

В панели Selectel откройте параметры подключения к S3 и скопируйте:

- S3 API endpoint;
- пул/регион.

Не составляйте endpoint вручную: он зависит от выбранного пула и текущей конфигурации Selectel.

Публичный домен и S3 API endpoint — разные адреса:

- backend отправляет команды загрузки и удаления на `S3_ENDPOINT`;
- браузер читает готовые изображения через `S3_PUBLIC_BASE_URL`.

## 4. Настройка сервера

После получения изменений из Git откройте backend:

```bash
cd /var/www/rf4/back
npm install
nano .env
```

Добавьте в `/var/www/rf4/back/.env`:

```env
MEDIA_STORAGE=s3

S3_ENDPOINT=https://API_ENDPOINT_ИЗ_SELECTEL
S3_REGION=ПУЛ_ИЗ_SELECTEL
S3_BUCKET=rf4-user-content
S3_ACCESS_KEY_ID=ACCESS_KEY_ИЗ_SELECTEL
S3_SECRET_ACCESS_KEY=SECRET_KEY_ИЗ_SELECTEL
S3_PUBLIC_BASE_URL=https://ПУБЛИЧНЫЙ_ДОМЕН_БАКЕТА
S3_KEY_PREFIX=user-content
S3_FORCE_PATH_STYLE=true
```

Правила заполнения:

- не ставьте кавычки вокруг ключей;
- не добавляйте `/` в конце endpoint и публичного домена;
- `S3_REGION` — именно пул из панели Selectel, а не произвольное значение;
- не добавляйте `.env` в Git и не присылайте Secret key в сообщения;
- локально оставьте `MEDIA_STORAGE=local` либо вообще не добавляйте эту переменную.

## 5. Проверка до перезапуска сайта

Сначала проверьте код и подключение отдельно от работающего приложения:

```bash
cd /var/www/rf4/back
npm run typecheck
npm test
npm run storage:test
```

Последняя команда выполняет полный безопасный тест:

1. загружает временное PNG-изображение;
2. открывает его через публичный домен;
3. удаляет тестовый объект.

Успешный вывод выглядит примерно так:

```text
S3 upload succeeded: https://...selstorage.ru/user-content/posts/<uuid>.png
Public read succeeded: HTTP 200
Test object deleted
```

Если получен HTTP 403, загрузка работает, но бакет не является публичным либо неправильно настроено чтение. Если ошибка возникает на загрузке, проверьте endpoint, регион, ключ и политику сервисного пользователя.

## 6. Включение в приложении

После успешного `storage:test` перезапустите backend с обновлением переменных:

```bash
pm2 restart rf4-api --update-env
pm2 logs rf4-api --lines 100
```

Проверьте по очереди:

1. создайте черновик поста с фотографией;
2. откройте фотографию в ленте и в самом посте;
3. убедитесь, что URL начинается с публичного домена S3;
4. удалите черновик и проверьте, что объект исчез из бакета;
5. загрузите новый аватар и сохраните профиль;
6. замените аватар и убедитесь, что предыдущий объект удалён.

Новые фотографии будут находиться в:

```text
user-content/posts/<uuid>.<расширение>
user-content/avatars/<uuid>.<расширение>
```

## 7. Откат

Если S3 временно недоступен, верните в `.env`:

```env
MEDIA_STORAGE=local
```

и выполните:

```bash
pm2 restart rf4-api --update-env
```

Новые загрузки снова пойдут в `back/uploads`. Уже сохранённые S3-ссылки продолжат открываться, пока бакет доступен. Не удаляйте бакет при таком временном откате.

## 8. Резервные копии

Резервные копии базы нужно хранить в отдельном **приватном** бакете, например `rf4-backups`, с отдельной политикой и жизненным циклом. Не складывайте дампы PostgreSQL в публичный бакет пользовательских изображений. Автоматизацию резервных копий следует включать отдельным этапом после проверки загрузок постов и аватаров.
