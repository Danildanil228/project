# ADR-001: предметный модуль как часть модульного монолита

Статус: принято.

## Контекст

Проект уже использует React, Express, PostgreSQL, SQL-миграции и сервисный слой. Новые точки, уловы, карты и аналитика тесно связаны с существующими пользователями, постами и модерацией.

## Решение

- сохраняем единое приложение и базу данных;
- новые области группируем по предметным модулям;
- вводим отдельный `catch_event`, не меняя смысл старой `catch`;
- стабильные машинные значения храним на английском, подписи переводим на frontend;
- исходные события и агрегаты храним раздельно;
- фоновые процессы добавляем только при появлении импорта и аналитики.

## Причины

- транзакции между постом, модерацией и уловом остаются простыми;
- эксплуатация на одном VPS остается понятной;
- границы модулей можно выделить позднее при доказанной нагрузке;
- отсутствуют расходы на преждевременную распределенную систему.

## Последствия

- сервисы не обращаются к таблицам чужого модуля без явно определенного контракта;
- тяжелая аналитика не выполняется в публичном HTTP-запросе;
- миграции должны сохранять совместимость с существующими данными;
- API и типы группируются по feature-областям, даже пока физическая структура старых модулей остается прежней.
